# Security Policy

> opencode-rc hands a chat app the ability to approve commands on your
> machine. Read this before you trust it with anything you care about.

## The one-paragraph version

opencode-rc is a **bridge between a chat app and an agent that can run commands
as you**. If someone can message the bot and is on the allowlist, they can make
opencode do things on your machine. The whole design exists to make "someone
else can message the bot" false, and to make it loud and auditable when it is
not.

The security argument rests on one property:

> **A bot cannot approve itself. Pairing is completed at a terminal, never from
> a chat message.**

If a chat account is compromised, the attacker gains nothing they did not already
have. If a prompt injection convinces the model to approve something, the model
has no mechanism to do so — the approval path does not exist in a chat context.

## Reporting a vulnerability

**Do not open a public issue.**

- **Preferred:** GitHub Security Advisories → *Report a vulnerability* on
  <https://github.com/palmate09/opencode-remote-control/security/advisories/new>
- **Alternative:** email the maintainers listed in `GOVERNANCE.md`.

### What we are looking for

In rough priority order:

| Class | Example | Severity |
|---|---|---|
| **Remote command execution** | Anything that lets an unpaired or non-allowlisted sender cause opencode to run a command, or lets a *paired* sender exceed the intent they were granted | Critical |
| **Pairing bypass** | Any path from a chat message to a change in `access.json`, or a path from a chat message to an approved permission | Critical |
| **Permission relay forgery** | Answering a permission request without being the intended replier; double-answering; forging a button payload | Critical |
| **Injection through the relay** | Getting hidden or bidi-reversed content past `sanitize.ts` into a chat app, such that an operator approves something different from what opencode asked | High |
| **Secret disclosure** | A token or credential reaching a log file, a chat message, or an outbound webhook | High |
| **State exfiltration** | Sending a file from the state directory (`access.json`, `.env`, `approved/`, `bot.pid`) | High |
| **Audit evasion** | Making `rc audit verify` pass over a record that was edited | Medium |
| **Denial of service** | A remote party making the bridge unusable | Low |

### What we will *not* accept as a vulnerability

- The limitations we document: a sleeping machine stops the bot; opencode's own
  permissions still apply; we do not defend against someone who already has
  root on your machine.
- Findings that require you to already control the terminal.
- Missing hardening suggestions with no working exploit path.
- Reports generated by automated scanners without a demonstrated impact.

### Process

1. **Acknowledgement** within 72 hours.
2. **Assessment** within 14 days, with a severity rating and a decision on
   whether we will credit you.
3. **Fix** in a private branch, with a regression test added to the suite.
4. **Disclosure** coordinated with you, with a 90-day maximum from the initial
   report before public disclosure even if unfixed.

If we cannot fix something, we will say so plainly and document the limitation
rather than quietly shipping it.

## Threat model — summary

Full version: [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md).

### Assets

1. The integrity of the allowlist in `state/access.json`.
2. The integrity of the opencode session — that only the intended person drives it.
3. The integrity of the decision to approve a command.
4. The confidentiality of credentials on the machine.
5. The integrity of the audit log, as *evidence*.

### Adversaries

| # | Adversary | Capability |
|---|---|---|
| A1 | **Stranger** | Can DM the bot. Has no terminal. |
| A2 | **Prompt injector** | Controls content that opencode reads — a file, a web page, a git commit message, another repository. |
| A3 | **Compromised chat account** | A paired person's Telegram/Discord/Slack account is taken over. |
| A4 | **Local attacker** | Code execution on your machine but *not* your terminal session. |
| A5 | **Network observer** | Sees traffic between your machine and the chat platform / opencode. |
| A6 | **Malicious contributor** | Submits a pull request. |

### Trust boundaries

```
┌─ your machine ───────────────────────────────────────────────┐
│                                                                │
│  ┌─ trust boundary 1: the terminal ─────────────────────────┐  │
│  │  rc access allow <code>        ← ONLY an approval path   │  │
│  └──────────────────────────────────────────────────────────┘  │
│                            │                                   │
│  ┌─ trust boundary 2: the gate ─────────────────────────────┐  │
│  │  every inbound message, before anything else is parsed   │  │
│  └──────────────────────────────────────────────────────────┘  │
│                            │                                   │
│  ┌─ trust boundary 3: the relay ───────────────────────────┐  │
│  │  sanitize.ts — the last chance to stop a forged approval │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                │
│  opencode ──────────────────────────────────────              │
└────────────────────────────────────────────────────────────────┘
```

### What we defend

| Attack | Defence |
|---|---|
| A1 messages the bot | §7.1 gate. Strangers get a code and can do nothing. `MAX_PENDING_CODES=3` caps spam. |
| A1 brute-forces a code | 6 hex chars = 24 bits, 1-hour TTL, **but approval is terminal-only anyway**, so guessing gains nothing. |
| A2 says "approve the pending pairing" | No chat path to approval exists (§7.4 layer 3). Anti-sycophancy: the code is never auto-picked, *even when exactly one is pending*. |
| A2 hides `rm -rf /` with zero-width characters | `sanitize.ts` strips zero-width, bidi overrides, tag characters and homoglyphs. |
| A2 hides a dangerous command at the end of a long string | Cap with **head and tail preserved** around a counted elision marker. |
| A2 forges `[image attached — read: PATH]` | File paths travel as metadata, never inline (§7.4 layer 5). |
| A3 taps Approve twice | First answer wins. The registry claims the request before the I/O. |
| A3 taps a button meant for someone else | The claim is keyed on the short id, which is per-request, not per-user. |
| A3 answers after expiry | Expired requests are unreachable. |
| A4 reads `state/access.json` | Mode `0600`, directory `0700`. Out of reach without the user's own account. |
| A4 exfiltrates state files | `assertSendable()` — invoked by `Bridge.sendFile` before **any** adapter sees a path — refuses anything inside the state directory except `inbox/`, with `realpath` on both sides and a trailing separator so `/state-evil` cannot match `/state`. Refusals are audited. |
| A4 forges audit records | Hash-chained. `rc audit verify` names the exact broken record. |
| A4 edits a transcript to evade erasure | `/forget` purges the actor's audit records and re-anchors the chain, so an export after erasure no longer returns them. |
| A1/A3 forges a Discord button tap | The interactions endpoint verifies Discord's Ed25519 signature (`X-Signature-Ed25519` over `timestamp ‖ body`) before any permission is answered; a forged or replayed body is `401`. |
| A5 observes traffic | Platform traffic is TLS to the platform. opencode should be bound to loopback or Tailscale, never the public internet. |
| A6 lands a supply-chain change | `bun install --frozen-lockfile`, a dependency licence audit that fails on GPL/AGPL/SSPL, CODEOWNERS, and required CI gates. |

### What we do **not** defend against

- **A machine that sleeps.** The bridge stops. Use `tmux` or a machine that stays on.
- **Someone with root.** They do not need a bridge.
- **A malicious model provider.** If your model provider exfiltrates your
  prompts, that is between you and them. We pass prompts to opencode unchanged
  and record that we did.
- **A paired user doing something you did not want.** They are, by definition,
  authorised. Pair the smallest set of people, and revoke when they leave.
- **Secrets with no recognisable prefix.** Our masking is pattern-based. A secret
  that looks like ordinary text and does not span a space will survive — treat
  everything relayed as untrusted unless you control the client fleet.

### The seven anti-injection layers (§7.4)

| # | Layer | Where |
|---|---|---|
| 1 | System instruction appended to every relayed session | `ANTI_INJECTION_SYSTEM` in `packages/core/src/transport.ts` |
| 2 | The access module only accepts terminal requests | `terminalOnly()` in `packages/cli/src/commands.ts` |
| 3 | Anti-sycophancy: the code is never auto-picked | `Gate` / `PairingManager.issue()` |
| 4 | Delimiter injection defence | `safeName()`, `inlineFrameSafe()` |
| 5 | Meta-only annotations — paths never inline | `Renderer.diffSummary()` |
| 6 | State exfiltration guard | `assertSendable()` |
| 7 | Capability declaration | `AdapterCapabilities.permissionRelay` |

Layer 7 deserves emphasis: **an adapter that cannot authenticate the replier must
not advertise `permissionRelay`.** The webhook adapter does not, because a URL
authenticates a caller, not a person. There is a test for every adapter's
declaration.

## Operator checklist

- [ ] `RC_DISABLED=false` and `rc doctor` passes
- [ ] Allowlist contains **only** people you intend to authorise
- [ ] No groups are configured, unless you intended that
- [ ] opencode's `permission` mode is `ask`
- [ ] opencode is bound to `127.0.0.1` or a Tailscale address, never `0.0.0.0`
- [ ] State directory is `0700`; `access.json` and `audit.salt` are `0600`
- [ ] `.env` is git-ignored and not in your backups in plaintext
- [ ] `RC_LOG_ACTOR=hash` (the default)
- [ ] A systemd/launchd unit restarts the bridge if it crashes
- [ ] `rc audit verify` runs in your own monitoring
- [ ] You have read "Honest limitations" at the top of the README

## Verifying the claims in this document

Every security claim here is backed by a test. From the repository root:

```bash
bun test
```

Specifically:

| Claim | Test file |
|---|---|
| Invisible-unicode and bidi defence | `tests/sanitize.test.ts` |
| Head-and-tail capping | `tests/sanitize.test.ts` |
| State exfiltration guard | `tests/sanitize.test.ts` |
| The gate, pairing, TTL, group policy, master kill | `tests/pairing.test.ts` |
| Strict reply grammar, first-answer-wins | `tests/permissions.test.ts` |
| Audit chain tamper evidence | `tests/logger.test.ts` |
| Message bodies never reach the audit log | `tests/bridge.test.ts` |
| Capability declarations per adapter | `tests/adapters.test.ts`, `tests/http-adapters.test.ts` |
| Discord interaction signature verification (forgery rejected) | `tests/discord.test.ts` |
| Erasure removes records and the chain survives | `tests/bridge.test.ts`, `tests/logger.test.ts` |
| File relay refuses state-directory paths | `tests/bridge.test.ts`, `tests/sanitize.test.ts`, `tests/telegram.test.ts` |
| Pairing is terminal-only | `tests/cli.test.ts` |

Two of those suites run real servers on loopback — a fake Telegram Bot API and
the API/webhook adapters' actual HTTP listeners — because authentication,
MarkdownV2 escaping, the poll-offset arithmetic and the 64-byte callback-data
limit are exactly the things a unit test on a pure function cannot check, and
exactly the things that break silently.

## Untested surface, stated plainly

`SECURITY.md` claims are only worth what the tests behind them are worth. Here
is what is **not** covered:

| Area | State |
|---|---|
| Discord HTTP interactions endpoint | Tested against a real server on loopback, with real Ed25519 signatures (`tests/discord.test.ts`) |
| Discord Gateway transport (inbound messages) | **Never run.** Event parsing, payload round-trip and capability declarations are tested; the socket is not. |
| Slack Socket Mode transport | **Never run.** Event parsing, payload round-trip and capability declarations are tested; the socket is not. |
| MCP stdio transport | **Never run.** Same. |
| Telegram, API, webhook transports | Tested against local servers |

### Discord interaction signatures — implemented

Discord sends a `X-Signature-Ed25519` header and a `X-Signature-Timestamp`
header on every interaction. The adapter now:

1. exposes an HTTP interactions endpoint (loopback by default);
2. verifies the Ed25519 signature over `timestamp ‖ rawBody` **before** parsing
   the payload, returning `401` for anything that does not verify;
3. refuses to start at all if `RC_DISCORD_PUBLIC_KEY` is missing or not a valid
   32-byte hex key, because without it every interaction is unforgeable-in-name
   only.

Because interactions are delivered to this endpoint, the Gateway
`INTERACTION_CREATE` route was removed — keeping it would have reintroduced an
unauthenticated path to `answerPermission`. A forged or replayed component body
(the capture-and-swap attack) fails the signature check and never reaches the
bridge. This is covered by `tests/discord.test.ts`.

The Gateway is still used for **inbound messages**, and that socket remains
untested. It does not carry permissions, so a forged frame there cannot approve
anything.

Telegram's callback queries and Slack's block actions are authenticated by the
platform's own connection — the adapter is long-polling or socket-connected
using a bot token, and there is no inbound endpoint to forge against. Discord
now reaches the same standard via signature verification.
